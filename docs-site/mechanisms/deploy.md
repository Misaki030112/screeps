# 部署

游戏跑的不是仓库里的 `src/` 目录结构。上传前，`scripts/build.js` 把 `src/**/*.js` 摊成 `dist/` 里一层的模块，并把 `require` 改成摊平后的名字。Screeps 的用户代码接口要的是这一层名字。

`node scripts/check.js` 做四件事：重新构建，对每个摊平后的文件跑语法检查，用一份房间快照做 600 tick 的模拟，再跑 `tests/` 里的单元测试。测试覆盖身体、地板、外矿状态机、实验室搬运这类纯逻辑。模拟用的快照会过时，大改之前应该换成当时的房间，但检查本身不连真实服务器。

`node upload.js` 先跑检查，再读取执行上传的那台机器上的令牌，把 `dist/` 传到分支 `default`（参数可以换分支名）。令牌只留在执行上传的那台机器上，不进仓库。仓库、手册和这个网站都不包含它，也不包含任何控制台密码。

另一条常用路径是仓库里的 `scripts/deploy.py`：同样先检查，再上传，并在部署期间放一把锁，避免两个人同时传。锁和上传记录是操作细节。公开手册只保证一件事：没过检查的代码不应该成为 shard3 上的 `default`。

`dist/` 也不进 git。它是构建产物。别人克隆仓库之后要自己跑检查，才会得到同一份摊平结果。

## 这本手册怎么单独发布

手册是仓库里的 `docs-site/`，用 VitePress 做成静态站。根上的 `vercel.json` 让 Vercel 在导入整个 Git 仓库时只安装、只构建这个目录，输出 `docs-site/.vitepress/dist`。游戏代码没有 `package.json`，也不会被当成网站去编译。

网站不需要环境变量。没有令牌、没有数据库、没有内网地址。房间名和上面这些机制是公开的游戏设计。

本地预览：

```bash
cd docs-site
npm ci
npm run dev
```

构建：

```bash
cd docs-site
npm run build
```

## 为什么检查要先于上传

摊平后的一个错误 `require` 会在游戏里变成整拍脚本失败，房间停在上一份代码上，或者更糟，停在一份半新的代码上。语法检查抓书写错误，单元测试抓地板和身体这种回归，模拟抓「这份快照上循环至少能跑完」。它们不证明下一小时的经济是健康的。那是部署之后的事，不写进这个站点。
