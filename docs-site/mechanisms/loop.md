# 主循环与 CPU

Screeps 每个 tick 调用一次 `loop`。这套代码把这一拍切成固定的几段，而不是让每个 creep 自己决定全世界。顺序写在 `src/main.js`。

## 每一段在干什么

先碰一次 `Memory.creeps`，让解析内存的开销落在统计里，然后删掉已经死掉的 creep 记忆。接着孵化：W47N8 的出生点进 `rooms/w47n8` 的 `spawnRun`，别的出生点进家里的 `managers/spawn`。

然后扫已占领的房间。W47N8 只在这里跑自己的布局和塔。家和其他属于我们的房间跑布局、塔、link、实验室和警报。外矿房间没有控制器所有权，所以不进这一支；它们的警报在外矿管理器之后补一刀。

外矿管理器更新威胁状态。道路管理器在 RCL6 以下什么也不做。若人打开了 `Memory.cmd`，指挥官可以接管一座建筑或一只 creep；没打开时，这些检查就是几次假值判断，和平时期的角色脚本不会被改写。

最后才是 creep。被墙封住的出生格先尝试解开。没有角色的 creep 暂时当成采集工，避免一只空记忆的单位什么都不做。家的非战斗单位若发现家里有需要躲开的东西，会先走 `home.flee`。守卫、探针、袭击、征服、W47 的 creep 和 `reserve7` 不走这条逃跑。

循环末尾写能量账、跟踪、统计，并打一行 `STATS`。这行是给人看的摘要：时间、用掉的 CPU、桶、错误数。它不决定下一只 creep 去哪。

## 20 这个数字在哪里

Shard3 上这个账号的每 tick 限额是 **20**。源码不写死 20，也不自己裁剪到 20。它读当场的 `Game.cpu.tickLimit` 和 `Game.cpu.bucket`。桶是没用完的限额积下来的储备，上限通常是 10000。平时一拍用掉几单位，桶是满的，循环按 `Game.creeps` 的原顺序跑完。

桶一旦低于 **2000**（`cpuorder.LOW`），两件事发生。

第一，顺序改成：战斗角色优先，然后是女王和 W47 的 filler（它们给出生点和塔补能量），其余经济单位排在后面。战斗打不出去、塔也没补上，省下的 CPU 没有意义。

第二，非优先单位在本拍已用 CPU 距离 `tickLimit` 不足 5 时直接跳过。跳过的是一整拍的意图，包括寻路。这样脚本不会在防御 creep 还没跑、统计还没写的时候被硬切断。被跳过的单位下一拍再动，路径缓存还在，不会因为这一拍没走就报卡住。

外矿防御另有一道 **3000** 的桶门槛。低于它，状态机给出的理由是 `cpu`，不把一只很贵的防御 creep 排进队列。房间视觉在桶低于 2000 时不画。把桶维持在 5000 以上是人的习惯：留出余量给突然出现的入侵者。代码不强制 5000。

## 为什么要停一拍，而不是把所有人写得更短

每只 creep 都找一次路，桶会在战斗那一拍被掏空，然后接下来几千 tick 都在还债。停一拍让经济单位晚一点捡能量，存储和容器扛得住这点延迟。防御单位和补能单位扛不住「这一拍没跑」。

所有段落都包在 `utils/errors` 里。一段抛错，其余段继续，错误留在统计里，而不是让整拍脚本死掉。
